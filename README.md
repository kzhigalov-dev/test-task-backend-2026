# Синхронизация CRM → PostgreSQL

В исходном варианте каждый объект вызывал поиск и commit, а очистка повторно читала всю таблицу; ошибки сделок скрывались. Теперь существующие строки читаются один раз, поиск выполняется по индексам в памяти, изменения записываются пакетами, а полная очистка выполняется только после успешного чтения обеих выгрузок. Запись и очистка входят в одну транзакцию: ошибка чтения или записи приводит к rollback и передаётся вызывающему коду.

Сохранены JSONB и общий `abstract_customer`: покупатель и сделка связаны принадлежностью одной строке. Это связь через общего владельца, а не отдельная связь каждой пары покупатель—сделка. При слиянии сохраняется id строки сделки и объединяются все четыре массива и `send_methods`. Для поиска по логину неоднозначность определяется числом разных строк, а не объектов внутри одной строки. Повторяющиеся CRM id в разных строках считаются ошибкой, чтобы не выбирать произвольную запись. При полной выгрузке пустой результат означает удаление всех ранее сохранённых владельцев; имена с «удалить» исключаются без учёта регистра. Для частичной выгрузки сохранены исключения статусов и очистка не выполняется.

## Запуск

Требуются Python 3.9+, PostgreSQL и Flask application context. Установка и проверка на **отдельной тестовой базе** (тесты удаляют и создают таблицы):

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export TEST_DATABASE_URL='postgresql+psycopg://user:password@localhost:5432/sync_test'
python -m pytest -q
```

Для новой базы `db.init_app(app)` и `db.create_all()` в контексте Flask создают таблицу и индексы. На существующей базе примените `migrations/001_jsonb_indexes.sql`, например `psql "postgresql://user:password@localhost:5432/dbname" -f migrations/001_jsonb_indexes.sql`. Создание индексов обычным `CREATE INDEX` блокирует записи на время построения; для рабочей базы планируйте окно обслуживания.

Клиента CRM в задании нет. Подключите его через `collect_leads_customers(is_full=True, crm_get=client.get)` или замените `main.amocrm_get`. Функция вызывается в Flask context, получает класс `Customer` или `Lead` и именованный `_with`, возвращает итератор объектов с `id`, `name`, `status_id`, `custom_fields_values`, `get_field`, `as_dict`, `contacts`, `companies`. Элементы `contacts`/`companies` содержат `id`; имеющиеся вложенные записи сохраняются по этим id, самих данных для загрузки новых контактов/компаний в предоставленном интерфейсе нет. Исключения клиента не перехватываются. Полная выгрузка обязана быть полной, включая корректное завершение итераторов; пустую выгрузку считать ошибкой должен сам клиент, если это нештатно.

GIN `jsonb_path_ops` поддерживает точное включение по id, логину и названию в обоих JSONB-массивах. Например:

```sql
SELECT * FROM abstract_customer WHERE amo_customers @> '[{"general":{"login":"alice"}}]'::jsonb;
SELECT * FROM abstract_customer WHERE amo_leads @> '[{"general":{"name":"Сделка"}}]'::jsonb;
```

## Объём и ограничения

Пусть `R` — число сохранённых строк, `E` — всех вложенных объектов в них, `S` — размер их сериализованного JSON, `N` — объектов новой выгрузки. Память порядка `O(R + E + S + N)` с коэффициентом на Python-объекты, словари и индексы; одновременно загружается **вся существующая база**, в том числе данные вне выгрузки. Оценка для 20 000 покупателей и 50 000 сделок: при среднем JSON 2 КБ на объект это около 140 МБ сырых данных; при расширении в 3–6 раз и 100–300 МБ на индексы/владельцев ориентир 0,5–1,2 ГБ RSS. Размер контактов, компаний, методов и payload CRM может существенно изменить оценку; её нужно измерить на реальных данных.

При размере пакета 500 выполняется один `SELECT`, затем до `ceil(I/500)` вставок, `ceil(U/500)` обновлений и `ceil(D/500)` удалений, плюс завершение транзакции, где I/U/D — числа итоговых строк каждой категории. Например, при 70 000 новых независимых строках — 1 SELECT + 140 INSERT + COMMIT; при 70 000 обновлённых — 1 SELECT + 140 UPDATE + COMMIT. Каждый пакет — один SQL statement с несколькими строками; фактические сетевые обмены протокола драйвера могут отличаться от числа statements. Тест проверяет 1 SELECT и 3 INSERT для 1100 строк.

Предполагается единственный пишущий процесс на время ночного запуска: параллельные сборщики и изменения таблицы приложением могут потерять обновления после снимка. Обеспечьте внешнюю сериализацию всех записей. Длительная транзакция и полная загрузка в память ограничивают масштаб; для больших баз нужны потоковая загрузка/временные таблицы и отдельная стратегия конкурентного доступа.
