# Синхронизация CRM → PostgreSQL

Решение [тестового задания](TASK.md). Python 3.9+, Flask, SQLAlchemy, PostgreSQL.

## Что изменено

Раньше каждая сущность требовала поиска и commit, очистка повторно читала таблицу, а ошибки сделок подавлялись.

Теперь таблица читается один раз, сопоставление по CRM id и логину выполняется через словари в памяти. Изменения записываются пакетами по 500 строк. Сбор, слияния и очистка входят в одну транзакцию: при ошибке выполняется rollback. Очистка запускается после успешной полной выгрузки.

Исправлены обновление сделки после слияния, перенос вложенных сущностей и удаление записей с «удалить» в имени. Неоднозначный логин не используется; несколько совпадений внутри одного владельца считаются одним совпадением.

## Что сохранено и почему

JSONB сохранён, чтобы обойтись без переноса данных. Покупатели и сделки связаны общим `abstract_customer`; при слиянии сохраняется id владельца сделки. GIN-индексы поддерживают точный поиск по CRM id, логину и названию через `@>`:

```sql
SELECT * FROM abstract_customer
WHERE amo_leads @> '[{"general":{"login":"alice"}}]'::jsonb;
```

Клиент CRM подключается через `collect_leads_customers(is_full=True, crm_get=client.get)` в контексте Flask. Он возвращает итераторы `Customer` и `Lead`. Существующие контакты и компании сохраняются по ссылкам из выгрузки; загрузка новых подробных данных о них остаётся задачей клиента. Частичный запуск сохраняет исключения статусов и не выполняет очистку.

## Проверка и установка индексов

Тесты пересоздают таблицу: используйте отдельную базу PostgreSQL.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export TEST_DATABASE_URL='postgresql+psycopg://user:password@localhost:5432/sync_test'
python -m pytest -q
```

Для новой базы `db.create_all()` создаёт таблицу и индексы. Для существующей примените [SQL-миграцию](migrations/001_jsonb_indexes.sql) через `psql` в окно обслуживания: создание индексов блокирует записи.

## Оценка нагрузки

Для 20 тыс. покупателей и 50 тыс. сделок при среднем JSON 2 КБ получается около 140 МБ исходных данных. С учётом Python-объектов и индексов ориентир памяти процесса составляет 0,5–1,2 ГБ. Это расчётная оценка; размер вложенных данных и всей существующей таблицы может её увеличить.

Число SQL-запросов: `1 SELECT + ceil(I/500) INSERT + ceil(U/500) UPDATE + ceil(D/500) DELETE`, затем один commit. Здесь I/U/D — количество вставляемых, обновляемых и удаляемых строк. Для 70 тыс. независимых новых строк это 141 запрос и commit. Пакетность вставок, обновлений и удалений проверяется тестами.

Решение загружает всю таблицу в память и требует единственного писателя на время запуска, иначе возможна потеря параллельных изменений. Успешная пустая полная выгрузка очищает таблицу; клиент должен отличать её от сбоя API.
